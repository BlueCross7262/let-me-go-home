# AI Slop Cleaner

AI 가 만든 코드 slop 을 범위를 넓히거나 의도된 동작을 바꾸지 않고 정리한다.
동작은 하지만 부풀어 있고, 반복적이고, 테스트가 약하고, 과잉 추상화된 코드를
위한 경계가 정해진 정리 워크플로우다.

## When to Use

아래에 해당하면 쓴다:
- 사용자가 `deslop`, `anti-slop`, `AI slop` 이라고 명시한다
- 시끄럽고, 반복적이고, 지나치게 추상적인 코드를 정리·리팩토링해 달라는 요청이다
- 후속 구현이 중복 로직, 죽은 코드, 래퍼 계층, 경계 누수, 약한 회귀 커버리지를 남겼다
- 사용자가 `--review` 로 리뷰 전용 anti-slop 패스를 원한다
- 목표가 새 기능 전달이 아니라 단순화와 정리다

## When Not to Use

아래에 해당하면 쓰지 않는다:
- 주로 새 기능 구축이나 제품 변경인 작업
- 사용자가 점진적 정리가 아니라 대규모 재설계를 원하는 경우
- 단순화·anti-slop 의도가 없는 일반 리팩토링 요청
- 동작이 너무 불명확해서 테스트나 구체적 검증 계획으로 보호할 수 없는 경우

## 실행 자세

- 사용자가 명시적으로 요청하지 않는 한 동작을 보존한다.
- 가능하면 먼저 표적 회귀 테스트로 동작을 고정한다.
- 코드를 고치기 전에 정리 계획을 쓴다.
- 추가보다 삭제를 택한다.
- 새로 만들기 전에 기존 유틸리티와 패턴을 재사용한다.
- 사용자가 명시적으로 요청하지 않는 한 새 의존성을 넣지 않는다.
- diff 를 작고, 되돌릴 수 있고, smell 에 집중된 상태로 유지한다.
- 간결하고 근거 밀도 높게 간다: 확인, 편집, 검증, 보고.
- 새 사용자 지시는 국소 범위 갱신으로 받되, 충돌하지 않는 기존 제약을 버리지 않는다.

## Scoped File-List Usage

호출자가 안전한 정리 범위를 이미 알고 있으면 이 스킬을 명시적 파일 목록이나
변경 파일 범위로 한정할 수 있다.

- 적합: `let-me-go-home:ai-slop-cleaner skills/ralph/SKILL.md skills/ai-slop-cleaner/SKILL.md`
- 적합: Ralph 세션이 그 세션에서 변경된 파일만 넘기는 경우
- 범위가 짧은 파일 목록이어도 같은 회귀 안전 워크플로우를 유지한다
- 사용자가 명시적으로 요청하지 않는 한 변경 파일 범위를 조용히 넓히지 않는다

## Ralph Integration

Ralph 는 이 스킬을 리뷰 이후의 경계가 정해진 정리 패스로 호출할 수 있다.

- 그 흐름에서 cleaner 는 `--review` 가 아니라 표준 모드로 돈다
- 정리 범위는 그 Ralph 세션의 변경 파일뿐이다
- 정리 패스가 끝나면 Ralph 가 완료 전에 회귀 검증을 다시 돌린다
- `--review` 는 기본 Ralph 연동 경로가 아니라 리뷰 전용 후속 모드로 남는다

## Review Mode (`--review`)

`--review` 는 정리 작업 초안이 나온 뒤의 리뷰 전용 패스다. anti-slop 작업에서
작성·검토 분리를 명시적으로 지키기 위해 존재한다.

- 작성 패스: 테스트로 동작을 고정한 채 정리 변경을 수행한다.
- 검토 패스: 정리 계획, 변경 파일, 검증 증거를 살핀다.
- 같은 패스가 영향 큰 정리를 쓰고 스스로 승인까지 하면 안 된다. 별도 검토
  단계를 거친다.

리뷰 모드에서:
1. 파일 편집으로 시작하지 않는다.
2. 정리 계획, 변경 파일, 회귀 커버리지를 검토한다.
3. 특히 아래를 확인한다:
   - 남아 있는 죽은 코드나 안 쓰이는 export
   - 합쳤어야 할 중복 로직
   - 여전히 경계를 흐리는 불필요한 래퍼나 추상화
   - 보존해야 할 동작에 대한 테스트 누락이나 약한 검증
   - 의도 없이 동작을 바꾼 것으로 보이는 정리
4. 필요한 후속 작업을 담은 검토 판정을 낸다.
5. 고치고 승인까지 한 번에 하지 말고, 필요한 변경을 별도 작성 패스로 넘긴다.

## Workflow

1. 현재 동작을 먼저 보호한다
   - 그대로 유지돼야 할 것을 짚는다.
   - 편집 전에 필요한 최소 회귀 테스트를 추가하거나 돌린다.
   - 테스트를 먼저 둘 수 없으면 코드를 건드리기 전에 검증 계획을 명시적으로 적는다.

2. 코드보다 정리 계획을 먼저 쓴다
   - 패스를 요청된 파일이나 기능 영역으로 한정한다.
   - 제거할 구체적 smell 을 나열한다.
   - 가장 안전한 삭제부터 위험한 통합 순으로 작업을 정렬한다.

3. 편집 전에 slop 을 분류한다
   - 중복 — 반복 로직, 복사·붙여넣기 분기, 군더더기 헬퍼
   - 죽은 코드 — 안 쓰이는 코드, 도달 불가 분기, 낡은 플래그, 디버그 잔재
   - 불필요한 추상화 — 통과용 래퍼, 예측성 간접층, 한 번만 쓰이는 헬퍼 계층
   - 경계 위반 — 숨은 결합, 잘못 놓인 책임, 엉뚱한 계층의 import 나 부수효과
   - 테스트 누락 — 고정되지 않은 동작, 약한 회귀 커버리지, 엣지케이스 공백
   - UI·디자인 기본값 — AI 가 만든 인터페이스가 검토 안 된 티를 내는 뻔한 시각 패턴

### UI/Design Reviewer Checklist

아래는 절대 금지가 아니라 검토 질문으로 쓴다. 브랜드, 접근성, 제품 밀도,
디자인 시스템상의 의도된 선택은 근거가 분명하면 그대로 둔다.

- 한국어 가독성: 본문이 11~12px 언저리로 잡혀 있으면 짚는다. 한국어 본문은
  검증된 고밀도 데이터 예외가 아니면 보통 최소 14px 가 필요하다.
- 그림자 절제: 표면·로고·배경·카드·아이콘 전부에 박스 그림자가 붙어 있으면
  의심한다. 고도나 상호작용을 분명히 하는 자리에만 남긴다.
- 콘텐츠 위계: 제목이 이미 메시지를 담고 있는데 eyebrow·제목·설명·추가 `<p>`
  가 반복되면 덜어낸다. 제품 목소리의 일부가 아니라면 뻔한 이모지 배지를 피한다.
- 팔레트 근거: 브랜드나 시스템 근거 없이 쓰인 기본 AI 블루·퍼플 팔레트, 특히
  Tailwind 계열 `#3B82F6` 을 의심한다.
- 레이아웃 리듬: 제품 맥락이 리듬·강조·비대칭·carousel·bento·가변 카드 비중에서
  이득을 볼 자리인데 지나치게 균일한 3열·4열 그리드를 쓰면 피한다.
- 그라디언트 절제: 브랜드가 의도적으로 그 시각 언어를 쓰는 것이 아니면 극단적
  그라디언트를 낮춘다.

4. smell 하나에 집중한 패스를 한 번에 하나씩 돌린다
   - Pass 1: 죽은 코드 삭제
   - Pass 2: 중복 제거
   - Pass 3: 네이밍·오류 처리 정리
   - Pass 4: 테스트 보강
   - 패스마다 표적 검증을 다시 돌린다.
   - 무관한 리팩토링을 같은 편집 묶음에 넣지 않는다.

5. 품질 게이트를 돌린다
   - 회귀 테스트를 초록으로 유지한다.
   - 손댄 영역의 lint, typecheck, 단위·통합 테스트를 돌린다.
   - 기존 정적 분석이나 보안 검사가 있으면 돌린다.
   - 게이트가 실패하면 밀어붙이지 말고 문제를 고치거나 위험한 정리를 되돌린다.

6. 근거 밀도 높은 보고로 마무리한다
   항상 보고한다:
   - 변경 파일
   - 단순화 내역
   - 동작 고정·검증 실행 결과
   - 남은 리스크

## Usage

- `/let-me-go-home:ai-slop-cleaner <target>`
- `/let-me-go-home:ai-slop-cleaner <target> --review`
- `/let-me-go-home:ai-slop-cleaner <file-a> <file-b> <file-c>`
- Ralph 에서: 그 Ralph 세션의 변경 파일만 대상으로 cleaner 를 돌리고, 정리 후
  회귀 검증을 위해 Ralph 로 돌아간다

## Good Fits

적합: `deslop this module: too many wrappers, duplicate helpers, and dead code`

적합: `cleanup the AI slop in src/auth and tighten boundaries without changing behavior`

부적합: `refactor auth to support SSO`

부적합: `clean up formatting`
